# 双模式客户端与不确定请求恢复

记录日期：2026-10-12。实现依据为 [API 契约](../upgrade/API_CONTRACT.md) 与 `packages/shared/src/api.ts`。本说明覆盖蓉城周末 Lab 与巷集 Select 的当前客户端行为，不声称公网 API、真实支付、微信或 App 设备运行已验收。

## 模式与数据归属

| 模式       | 数据权威与持久化                                                                               | 进入方式                                                           |
| ---------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 本地演示   | 旧版前端领域模型与当前设备存储；不产生服务端预约或订单                                         | 默认模式，或用户主动点击“本地演示”                                 |
| 服务端演示 | Fastify / SQLite 按演示会话保存数据；名额、库存、购物袋版本、优惠券、报价及订单状态由 API 确认 | 用户点击“连接本地服务”；之前明确选择的模式可保存并在刷新后重新连接 |

API 连接失败时保留服务端模式的断开状态与错误提示，不会偷偷切回本地模拟，也不会展示本地数据作为 API 成功结果。连接中、提交中或有待确认请求时禁止换模式；商城同样禁止以重置绕过未决请求。没有未决请求时的商城“重置”只重置当前服务端会话的模拟业务数据，不重置其他访客或旧版本地历史。

旧存储 `chenxi-pulse-v1` 与 `chenxi-shoppilot-v1` 保留；历史快照标为旧版本地记录，不自动上传、合并或改造成服务端订单。V2 使用独立模式、会话和待确认请求键，避免把两种数据所有权混在一起。

## 身份边界

| 客户端  | 身份                                                                                                     | 恢复要求                                                                                                    |
| ------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 预约 H5 | 服务设置的 `chenxi_h5` HttpOnly Cookie；路径 `/api/v1/h5`、SameSite=Lax；前端使用 `credentials: include` | 原 Cookie 仍有效；有未决请求时，连接必须发送 `{resumeOnly:true}`。缺失、失效或过期返回 401，不新建会话      |
| 商城    | `POST /api/v1/shop/demo/session` 返回的 24 小时演示 token，使用 uni storage 保存，后续以 Bearer 发送     | 保持原 token；有未决请求且 token 丢失 / 本地过期时直接阻止创建新身份。原 token 被服务器拒绝时保留待确认请求 |

H5 Cookie 与商城 token 不通用。SQLite 持久化与“在当前身份下能查询”是两个条件：数据库仍有历史数据，不代表丢失身份的客户端可以访问。当前没有账户登录、跨设备找回或凭订单号找回身份的接口。不得把新会话视作原会话，也不得向新会话重放旧预约、旧购物袋或旧订单请求。

## 发送前保存原意图

两个客户端写入前先同步保存以下字段：

```text
operation   业务操作名称，例如 bookings.create 或 orders.create
key         本次操作的 Idempotency-Key
path        原 API 相对路径
body        原 JSON 序列化字符串
```

H5 待确认键为 `chenxi-weekend-pending-v2`；商城为 `chenxi-select-pending-v2`。存储失败时不发送写入。再次提交如果操作、路径或序列化正文不同，会先要求处理原请求，不能生成新 key 覆盖原意图。重试使用原 key 与原 body，服务端在同一身份、同一操作作用域内执行幂等回放；同 key 不同正文报 `IDEMPOTENCY_CONFLICT`。

按钮的禁用与 loading 只是操作反馈，真正的结果由 API 和持久化状态确认。请求超时设为 12 秒；前端超时或网络中断不等于服务器回滚。服务端已完成写入但响应丢失时，保留原请求才可以在刷新后安全确认结果。

## 结果与恢复规则

| 收到的结果                                                                      | 客户端处理                                               |
| ------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 有效成功响应                                                                    | 清除活动待确认记录，刷新服务端业务数据                   |
| 首次提交收到确定的业务拒绝，例如名额不足、库存不足                              | 可清除该次待确认记录，展示错误，按页面需要刷新服务端状态 |
| 超时、网络失败、无效响应、5xx 或 429                                            | 保留原 key / body，显示查询与原请求重试入口              |
| 任何恢复重试失败，包括 401、SESSION_EXPIRED、UNAUTHORIZED、IDEMPOTENCY_CONFLICT | 保留原请求；这些错误不能证明先前提交从未发生             |
| operations 查询返回 SUCCEEDED                                                   | 确认原操作，清除活动待确认记录并刷新数据                 |
| operations 查询未找到或失败                                                     | 保留原请求；查询时未找到不能证明正在处理的原写入不会完成 |
| 身份丢失                                                                        | 阻止建立新身份来重放，允许保留记录或明确停止恢复         |

查询入口为 `GET /operations/:key?operation=...`，按 H5 / shop 各自前缀与身份访问。预约取消、购物袋变更、领券、报价和订单动作也使用幂等写入；取消按钮不直接修改服务器业务状态。

客户端通过代次标识保护异步状态：切换作用域或发起更新操作后，过期的商品查询、场次查询和旧记录刷新不能覆盖新结果。连接过程中不允许切换模式，避免旧连接的 finally 无法归还 loading 状态。预约取消后的记录也不会被先前尚未返回的刷新改回“已确认”。

## UNKNOWN 归档的含义

身份失效且存在待确认请求时，页面显示“停止原会话恢复”。H5 使用浏览器确认，商城使用 uni 确认框；提示明确说明原请求可能已成功，只归档本机请求，不撤销服务器结果，也不自动创建新会话。

用户确认后，客户端先将原 `operation`、`key`、`path`、`body` 保存至原待确认键加 `-archive-<key>` 的独立存储项，并加上 `abandonedAt` 与 `outcome: "UNKNOWN"`；然后清除活动待确认项。商城同时移除已不可用的本机会话记录。存档写入失败时不能悄悄丢弃原请求。后续新体验仍需用户手动选择。

**UNKNOWN 表示原业务结果仍未知。** 本机归档不包含可重建 H5 Cookie 的身份凭据，也不恢复丢失的商城 token。它不能找回旧身份、导入旧订单、取消预约、释放库存或证明服务端操作失败。当前没有归档导入 / 身份找回 UI。不要将归档当作待重新执行的队列，也不要把它自动发送到新会话。清理浏览器 / 设备存储还会使本机档案丢失。

演示身份过期后，业务历史可能仍存在于数据库，但原身份不可访问；后续清理也可能删除过期会话。当前方案的恢复边界是“原身份仍有效且原请求证据仍在”，并非永久账户或可靠离线同步系统。

## 业务权威与时间

H5 提交人数为 1–4，规则版本、场次截止、可用名额与同活动有效预约限制均由服务器检查；取消须服务器确认后显示。三题偏好是确定性路线推荐，不预留名额。只收可选虚构代号，不要求手机号或真实姓名。

商城金额使用整数分。购物袋变更携带 `cartVersion`；报价以服务器价格、优惠券规则和演示地址计算，有效期 120 秒，报价本身不预留库存。创建订单后由服务器原子预留库存及优惠券，待付款有效期 15 分钟。付款失败仍是待付款；取消、过期、发货和收货以服务器允许的状态迁移为准。UI 倒计时根据返回的 `serverTime` 修正，只提供提示，不能自行宣判付款或预约成功。

## API 对接与部署前提

开发默认 API 监听 `127.0.0.1:4016`，数据库路径 `.local/data/demo.sqlite`；`API_PORT` 与 `DEMO_DB` 可分别覆盖。两个 Vite 开发入口将 `/api/v1` 代理至该服务。完整本地步骤及测试命令见 [跨端验收矩阵](../acceptance/PLATFORM_RELEASE_MATRIX.md#复现本地服务端演示)。

预约客户端固定请求同源 `/api/v1/h5`，写入需要 JSON、`X-Chenxi-App: h5`、原生浏览器 Origin 和原 Idempotency-Key。部署需由 HTTPS 站点反向代理该路径，保留 Cookie、响应与幂等头。当前启动器服务是回环地址的本地演示进程；允许的 Origin 默认仅列出本机开发 / 预览来源。`createService({allowedOrigins})` 支持显式列表，但现有启动器未提供公网 Origin 环境变量。需要按部署目标补齐启动配置与验证，不能仅设置一个未经实现的环境变量后声称可上线。

当前本地 H5 Cookie 为 HttpOnly、SameSite=Lax，尚未设置 Secure；HTTPS 部署时需正确启用 Secure 并复核代理、会话过期与恢复行为。服务没有在本轮验收任意跨域 CORS。静态 Pages 也不提供 `/api/v1` 服务；不能把访客设备的 `127.0.0.1` 当成公网 API。

商城 H5 默认请求同源 `/api/v1/shop`。`VITE_SHOP_API_BASE` 是构建期 API 基址，可用于配置完整 HTTPS 地址；如使用跨域浏览器地址，须先实现并验证对应 Origin / CORS 约束。非 H5 产物必须配置以 `https://` 开头的 `VITE_SHOP_API_BASE`，否则服务端模式明确返回未配置错误。uni 公共客户端使用 `uni.request` 与 uni storage，不依赖浏览器 DOM、fetch 或 localStorage。

微信还需真实 AppID 与平台允许的请求域名，App 需平台标识、网络配置和设备验证。HTTPS 字符串校验、`urlCheck: true` 或资源编译成功均不能替代这些验证。部署还需可写且持久的数据库目录、备份和过期数据策略；不可上传 `.local` 中的会话数据库、token 或未经审阅的运行数据。

## 验证依据与限制

本轮客户端与旧有领域单测合计 54 项通过；独立 QA 另外验证了连接时切模式、过期刷新覆盖取消结果，以及真实 API 已提交后失去 Cookie 的恢复边界。应用级真实 Chrome 流程 7 / 7 通过，其中包含两个“服务端提交后丢响应”用例及两个身份丢失、确认 UNKNOWN 归档的用例。范围、命令、报告位置和平台限制详见 [跨端验收矩阵](../acceptance/PLATFORM_RELEASE_MATRIX.md)。

这些证据验证本次本机实现，不代表所有网络时序、存储故障、全部辅助技术、微信开发工具或 Android / iOS 运行时已覆盖。
