## 补充：SwiftShader 低算力诊断

2026-10-13 在本机 Windows、实际 Chrome **154.0.8037.94**、Playwright **1.64.0** 上做了独立诊断。浏览器显式使用 `--use-angle=swiftshader`；实际 WebGL 调试信息返回 `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)`，确认该次使用软件渲染。先开启减弱动效，再通过页面按钮切回三维，保留应用现有降级保护、相机操作和全部业务状态约束。

受控低算力组额外使用 CDP **4×CPU 节流**及真实浏览器录像，视口 1440×900、标准画质、DPR 1。连续三个实际渲染统计窗口出现：

| 观察时间（自诊断开始） | 上报累计帧数 | 实际渲染 P95 | 画面状态                    |
| ---------------------- | ------------ | ------------ | --------------------------- |
| 约 16.8 秒             | 374          | 83.3ms       | 三维 canvas 仍存在          |
| 约 19.9 秒             | 433          | 83.4ms       | 三维 canvas 仍存在          |
| 约 22.9 秒             | 491          | 99.9ms       | 自动切换二维，canvas 被移除 |

最后页面明确提示“持续检测到较慢帧率，已切换轻量星图，任务状态保持。”同一 runId、worldVersion 1、tick 0、delivery 0 和 ready 状态均保持，未记录 console error 或 pageerror。原始检查点、真实截图和录像保留在本机忽略目录 `.local/ci-browser-diagnostic/chrome-software-slow-r3/`，其中 `report.json` 记录全部条件，`final.png` 显示实际降级提示。

保留的无 CPU 节流、无录像对照位于 `.local/ci-browser-diagnostic/chrome-software-r2/report.json`：同为实际 SwiftShader，观察约 24 秒没有降级，后续 P95 约 33–50ms。因此不能推导“没有硬件 GPU 就一定降级”。两个诊断条件不同，不用它们量化单一因素的性能影响。

该结果证明了**持续低帧率会按产品保护逻辑移除三维 canvas**，从而可能与长时间、跨多个镜头的截图测试前提冲突。它不是 Ubuntu GitHub Runner 或 Chromium 156 的直接复现，不能单凭此确定原始 CI 超时的全部原因。诊断未改产品源码、保护阈值或业务数据；也没有关闭降级来获得测试通过。

这一受控诊断独立于前述六组正式活动场景测量，不混入其中的中位数、范围或长任务统计，不改变原始 `performance.json` 及其结论。

## 后续：主分支 CI 失败证据与按需绘制修复

主分支 CI run `38282884515` 实际为 **92 通过、2 失败**，两项失败均为独立的镜头复归像素比较。世界全景差异为 `0.08163496732026143`，跟随载体为 `0.0859092320261438`，原阈值均为 `<0.004`。这次是像素比较失败，并非第二个镜头定位 canvas 的超时；不能与此前一次 CI 的超时混写。原始日志保留在 `.local/v3/ci-main-first-failed.log`。

下载并实际查看的两个 `test-failed-1.png` 均已显示**二维 SVG 星图以及持续较慢帧率的降级提示**，而不是仍处于同一个三维相机的画面。图片在 `.local/v3/ci-main-first-artifacts/.local/e2e/results/` 内的全景、跟随两项测试目录。失败截图证明断言失败后的现场已经降级；由于这批上传物没有对应的 before/dragged/restored 三张采样图，单凭最终 PNG 不能精确定位降级发生在哪次截图读回之间。这项真实 CI 证据与先前 Windows 软件渲染诊断相符，但两者仍是不同环境、不同记录。

源码检查发现，旧版本在启用减弱动效、世界仍为 `ready` 或已 `paused` 时继续执行完整三维渲染循环。画面事实不变，软件渲染仍持续消耗资源，并可能积累足以触发保护的慢帧窗口。修复提交 `da9b6337be81f7d6650785071984d1d2eb73fb47` 改为：

- 减弱动效且世界不在 `running` 时，只在变化后安排一个 RAF；静止后不保留连续绘制回调。
- snapshot、镜头请求、选择、动效偏好、画质与尺寸变化，以及悬停进出、拖动、滚轮、键盘、标签重新可见和上下文恢复均会唤醒实际绘制。按需分支不使用连续帧限频的提前返回，避免丢掉短间隔更新。
- 静止与连续模式切换清空帧间隔窗口，不把闲置时间算成慢帧；没有连续间隔样本时的 P50/P95 为 0，不代表 GPU 耗时为 0。
- 普通动态模式仍连续绘制，运行中的业务状态照常推进；原有慢帧降档与二维保护阈值保留。卸载仍取消唯一待执行 RAF 并释放资源。

可观测 canvas 属性 `data-render-mode` 区分 `on-demand / continuous`，`data-raf-pending` 表示是否有下一次回调；`data-camera-request` 只在实际 render 后写入。镜头测试保留原像素阈值、runId、tick 和交付事实断言，并等待真实绘制更新；新增静止绘制检查没有替代原来的镜头像素比较。修复不以强制保持三维、关闭保护或放宽比较阈值获取通过。
