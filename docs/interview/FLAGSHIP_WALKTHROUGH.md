## 1. Intelligence Lab：执行和表现各自负责什么

**三个设计 Why**

1. **为什么执行引擎不依赖 3D？** `createRuntime` 维护业务状态，Three.js 和二维界面投影同一快照。WebGL 不可用、动画暂停或减弱动效不能替代审批，也不能宣布任务成功。默认二维保留完整操作，三维显式启用。
2. **为什么草稿、批准和写入分成步骤？** `workflowAction` 在查询、比较、草稿之后停在 `awaiting-approval`；`approve` 只授权，下一次 `step` 才写入隔离本地记录。拒绝应保持零写入，来源材料中的指令性文字也不能变成执行权限。
3. **为什么记录输入和逐步快照，而不在回放时重跑？** 同一计划可能已经写入；再次调用工具会让“查看历史”产生新副作用。`validateRecording` 校验结构与顺序，`replaySnapshot` 只取已记录状态。当前是确定性 fixture，不是已接入 LLM 的规划器。

**两个可触发的失败场景**

| 场景             | 实际操作                                                   | 预期观察与恢复                                                                                     |
| ---------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 预算不能满足候选 | 商品研究，将预算设为 1 元，生成计划、连续执行              | 比较节点失败、写入 0；改为 500 元后“按当前目标重新规划”。只改显示文字不能让失败节点自动成功。      |
| 工具超时         | 展开“验证异常与恢复”，将“下一工具注入”设为“工具超时”，单步 | 明确超时、保留失败节点；设回“无故障”，再“重试失败步骤”。仍处在注入超时状态时不能声称重试必然成功。 |

**现场异常验证（约 30 秒）：**运行第二个场景，先记录当前写入数为 0；超时后确认仍为 0，解除故障并重试到等待审批，再点“拒绝”。终态取消、写入仍为 0。这个结果来自执行约束，不来自动画是否播放完成。对应浏览器用例分别覆盖超时恢复与人工拒绝，不把这里的组合讲述说成新增测试。

**关键函数与已有证据：**[engine.ts](../../packages/intelligence/src/engine.ts)：`checkedGoal`、`createRuntime`、`execute`、`workflowAction`、运行时 `plan/step/approve/cancel/retry`；[recording.ts](../../packages/intelligence/src/recording.ts)：`validateRecording`、`replaySnapshot`；[IntelligenceLab.vue](../../apps/portfolio/src/pages/IntelligenceLab.vue)：`single`、`approve`、`openReplay`、`seek`。浏览器证据见 [intelligence.spec.ts](../../tests/e2e/intelligence.spec.ts) 中预算、超时/取消、审批拒绝和回放用例；功能评测范围见 [EVALUATION_REPORT.md](../intelligence-lab/EVALUATION_REPORT.md)。

## 2. 巷集 Select：库存、报价和未知结果

**三个设计 Why**

1. **为什么用整数分和服务端报价？** 客户端显示价格不能作为结算凭据。服务端 `quote` 根据购物车版本、地址与优惠券计算金额，生成有 120 秒有效期的报价；`createOrder` 再核对版本与库存。客户端只能提交 `quoteId`，不能提交任意实付金额。
2. **为什么加购物袋不占库存，创建订单才预留？** 浏览行为不应锁住稀缺商品。创建待付款订单才预留库存及优惠状态；付款、取消与 15 分钟到期释放由状态迁移处理。当前是每会话独立演示库存，不是跨用户生产商城。
3. **为什么失败后保留原键、原请求与身份？** 响应丢失时服务可能已经提交。`SelectClient.write` 在发送前持久化意图，`lookup/retry` 核对原操作；同键异体拒绝，身份丢失时不自动换会话。一次普通网络错误不能证明订单未创建。

**两个可触发的失败场景**

| 场景         | 环境与实际操作                                 | 预期观察与恢复                                                                                                     |
| ------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| SKU 售罄     | 纯静态“本地演示”：山间陶瓷杯选择“陶土棕”       | 加入购物袋被禁用，购物袋不增加；选择“沙岩白”后才能继续。这是库存约束的界面拒绝，不伪称已打到服务端。               |
| 模拟付款失败 | 本机 API：新建一张待付款订单，点“模拟付款失败” | 同一订单增加付款尝试，仍未付款，不直接发货；再“模拟付款成功”后才出现发货操作。不是支付渠道真实事故，也不发生扣款。 |

**现场异常验证（本机 API，约 30 秒）：**记录当前订单 ID，模拟付款失败，核对仍是同一条订单且出现“1 次付款尝试”；然后成功付款、发货、收货并刷新，确认该订单为已完成。若只有公网静态页面，改用结算页“模拟本次提交失败”：先观察购物袋保留，关闭注入后重试，核对本地订单只有一条；这一替代不能证明服务端幂等。

结果未知是另一项已测试边界：浏览器用例先 `route.fetch()` 确認 API 已成功，再中断返回响应，刷新后使用原请求重试并核对一单。普通 DevTools Offline 不能保证“先提交成功再丢响应”，现场不把这两种故障混为一谈。

**关键函数与已有证据：**[服务端 shop.ts](../../services/demo-api/src/shop.ts)：`quote`、`assertCart`、`createOrder`、`refreshShop`、`changeOrder`、`release`；[server.ts](../../services/demo-api/src/server.ts)：`post` 的幂等与归属处理；[SelectClient](../../apps/commerce-mini/src/v2/client.ts)：`connect/write/retry/lookup`；[服务模式 store.ts](../../apps/commerce-mini/src/v2/store.ts)：`createQuote`、`submit`、`action`、`recover`。静态分支在 [commerce.ts](../../apps/commerce-mini/src/domain/commerce.ts) 的 `setQuantity/calculate/placeOrder` 和 [shop store](../../apps/commerce-mini/src/stores/shop.ts) 的 `submit`。测试见 [commerce.spec.ts](../../tests/e2e/commerce.spec.ts)、[server-flows.spec.ts](../../tests/e2e/server-flows.spec.ts) 的 Shop 用例及 [server.test.ts](../../services/demo-api/src/server.test.ts)。

## 3. 蓉城周末 Lab：推荐理由不等于预约保证

**三个设计 Why**

1. **为什么推荐分数有明确组成？** `recommendRoutes` 用主题 +4、环境 +2、时长合适 +2 / 超时 −3 排序，并返回理由与取舍；余量不参与排名。适合用户的路线不一定还有可预约场次，推荐分与库存承诺分开。
2. **为什么以服务时钟、规则版本和提交校验为准？** 页面展示之后可能跨越截止时间或余量发生变化。`refreshH5/createBooking` 用服务时间和当前会话名额池检查状态、规则版本及人数；没有真实成功响应就不能把名额当作已确认。
3. **为什么每会话只允许一条有效预约，并把取消作为状态迁移？** 重复点击、刷新或同键重试不应多占名额；`createBooking` 检查有效预约，`cancelBooking` 对已取消记录直接返回，避免再次释放。旧本地预约不能算入服务端名额，结果未知时也不自动新建会话。

**两个可触发的失败场景**

| 场景                   | 环境与实际操作                                                             | 预期观察与恢复                                                                                         |
| ---------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 选择时间冲突           | 纯静态“本地演示”：先加入“把城市，印在纸上”，再加入“换个角度，读成都”       | 提示“时间有重叠”，第二项不加入；改选“灵感，不必等天亮”。这是本地日程校验，不能用于宣称服务端名额检查。 |
| 代号内容不符合演示约束 | 本机 API：进入有效场次预约页、选 2 人并勾选规则，虚构代号填 `演示@` 后提交 | 提示不要填写手机或邮箱，当前操作不发送创建预约请求；改为“橘子星人”后可继续。不要输入真实个人资料。     |

**现场异常验证（本机 API，约 40 秒）：**在浏览器 Network 保持记录，先用 `演示@` 触发表单拒绝，确认没有新增 `POST /api/v1/h5/bookings`；修正代号后提交，刷新仍有一条有效预约。取消并确认后返回原场次，核对余量恢复。只有公网时，演示上表的时间冲突，再使用提交页“模拟服务失败”保留草稿、解除注入后重试；说明全部记录仍在当前浏览器。

服务端响应丢失与身份丢失的既有测试在 `server-flows.spec.ts` 中：真实提交后丢响应、刷新后同键恢复一条预约；丢 cookie 的旧请求被拒绝恢复，新身份不会接管旧请求。该证据补充现场表单演示，不能把客户端校验当成服务端安全验证。

## 4. 金融事件回放：当前状态只能来自可信前缀

**三个设计 Why**

1. **为什么每次 seek 都重算当前连续前缀？** 先用完整序列算 K 线再截断，会泄漏未来最高价、成交量或收盘状态。`projectPrefix` 只应用游标以内、缺口之前的事件；当前六秒 K 线保持未收盘。72 条合成数据规模下，纯函数重算比复杂检查点更容易验证。
2. **为什么分别记录已接收和已应用事件，并按 ID/序号去重？** 收到后续序号不代表可以跨过缺失事件计算状态；重复投递也不能再次累加成交量。页面显示缺失序号、等待数和最后可信序号，回补后统一重算。
3. **为什么切换标的既取消请求又检查代次？** AbortController 只能请求取消，数据源可能仍迟到返回。`ReplayLoader.load` 同时核对 generation 和 signal，旧标的结果不能覆盖新选择。这里的异步源是本地合成序列准备，不是交易所网络。

**两个可触发的异常场景**

| 场景             | 实际操作                                                  | 预期观察与恢复                                                                                                                           |
| ---------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 连续事件出现缺口 | 时间轴到 10，移除当前事件，再单步一次                     | 前缀 `9 / 11`，序号 10 缺失、后续等待；点“回补并重算”恢复 `11 / 11`，不提前应用第 11 条。                                                |
| 当前事件重复投递 | 完整前缀时记录报价、簿中价/量和前缀，点“重复投递当前事件” | 重复计数增加，报价、簿和有效前缀不变；“重置”回到 `0 / 0`。成交量柱辅助观察，精确去重数值由领域测试断言。这是去重分支，预期不会抛错误页。 |

**现场异常验证（约 30 秒）：**在第 10 条执行缺口流程，逐项观察 `10 / 10 → 9 / 11 → 11 / 11`；回补后记录价格与簿中价/量，再重复投递，确认数值不变。成交量在界面只显示柱形，不把视觉一致当作精确数值断言；`replay.test.ts` 另外检查重复事件不改变 K 线和成交量。补充快速切换 `LUMEN → ATLAS`，等待准备完成后单步，ATLAS 首条价格应为 `100.00`。后者验证选择隔离；源码单测另外覆盖不响应取消的旧加载器，不能只凭动画推断取消成功。

**关键函数与已有证据：**[replay.ts](../../apps/portfolio/src/domain/market/replay.ts)：`syntheticEvents`、`projectPrefix`、`ReplayLoader.load/cancel`、`prepareSyntheticEvents`；[MarketReplay.vue](../../apps/portfolio/src/pages/MarketReplay.vue)：`step/play/pause/seek/selectSymbol/injectGap/injectDuplicate/recover/reset`。测试见 [replay.test.ts](../../apps/portfolio/src/domain/market/replay.test.ts) 与 [content.spec.ts](../../tests/e2e/content.spec.ts) 的“回放无未来数据、缺口重算、重复与切换取消”。
